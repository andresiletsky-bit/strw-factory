# State Protocol — робота з strw-state/

## Розташування
Приватний GitHub-репозиторій `strw-state`. Локальний клон — робоча копія петель. Notion — вітрина, односторонній sync через `strw-notion-sync`.

## Схема
```
strw-state/
├── company-context.md      # ДНК — читається ПЕРЕД будь-якою роботою
├── portfolio.md            # реєстр продуктів + WIP-ліміт
├── triage-inbox.md         # єдине місце ескалацій (append-top)
├── decisions-log.md        # gate-рішення (append-only)
├── budget.md               # стелі + факт
├── process-changelog.md    # версії процесу
├── loops-log/              # журнал запусків: YYYY-Www.md (append)
├── engine/                 # реєстр робочих item'ів + цикли рушія
├── _outbox/                # черга «контур C → Mac»
└── products/<id>/
    ├── state.md            # хребет: Done / In progress / Next / Tried & failed
    └── idea-card.md · validation-report.md · prd.md · build-report.md
```

`gates.json` (контракт гейтів циклу, default-FAIL) живе НЕ в strw-state, а в КОРЕНІ робочого дерева продуктового репо: створює його `strw-gates-init.sh` зі шаблону `bin/gates.<продукт>.template.json`, читає `strw-run` там само.

## Правила запису

1. **Читання перед роботою:** `company-context` + `portfolio` + `products/<id>/state.md`. Петля продовжує, не починає з нуля.
2. **`state.md` — після кожного циклу:** що зроблено, що спробували і провалили з причиною, що далі.
3. **append-only** для `decisions-log` і `triage-inbox` — записи закриваються статусом DONE.
4. **Рядок у `loops-log/YYYY-Www.md` після кожного запуску:** Дата · Петля · Продукт · Тривалість · Ітерації maker↔checker · First-pass · Вердикти · Ескалації · Моделі M/C. Це сировина для метрик L5 і патернів L6.
5. **Конфлікт стану** (два записи суперечать) → ескалація `question`, без вгадування.
6. **WIP-ліміт:** перед переведенням продукту в активну стадію порахувати активні в `portfolio.md`.

## Контур і запис у git

Стан комітить **контур M** — сесія на Mac із робочим тулчейном. Робить це `strw-run` або інтерактивна сесія, шляхово, ніколи `git add -A`.

**Контур C** (headless, хмара, пісочниця) складає результат у `_outbox/<YYYY-MM-DDTHH-MM>-<loop>-<product>.md` — звичайний файл, довільний вміст. На цьому його робота зі станом завершена: ескалації, факти бюджету, рядки loops-log — усе туди.

**У черги два кінці, і другий — обов'язок контуру M.** Сесія на Mac на початку роботи читає `_outbox/*`, вливає вміст у канонічні файли (`triage-inbox.md`, `budget.md`, `loops-log/`, `products/<id>/state.md`), комітить пошляхово і **видаляє злите з `_outbox/`**. Дата в імені файла — вік боргу: 07.08 у черзі лежало три файли, найстаршому вісім днів, і один із них устиг потрапити під версійний контроль так і не влитим. Перед вливанням звіряти, чи вміст уже не влито раніше — рядок за ту саму дату й петлю в `budget.md`/`loops-log/` означає дубль, а не збіг. Рядок прогону кладеться в тиждень **за датою заходу**, а не за поточним: захід 30.07 — це `2026-W31.md`.

Межу тримає `contour-guard.sh`, а не пам'ять агента: у контурі C git-команди на запис і мережу, а також виклики тулчейна повертають блок із поясненням, що зробити натомість.

**У контурі C кожна git-команда йде з `--no-optional-locks`, або не йде.** Читання (`log`, `show`, `status`, `diff`, `rev-parse`, `ls-tree`) з цим прапорцем дозволене. Запис і мережа (`add`, `commit`, `reset`, `checkout`, `push`, `pull`, `fetch`, `clone`, `remote`, `gc`) заблоковані завжди — прапорець їх не рятує.

**Чому одне правило замість переліку безпечних підкоманд.** Перелік звужували тричі, і щоразу реальність виявлялась ширшою: 05.08 лок від `commit`/`reset`, 06.08 від `git fetch` у `pact-ios`, 07.08 10:28 від `git status` у трьох репо одразу, того ж дня — від `git log` у `pact-backend`. Модель «команда на читання не бере лок» просто хибна: індекс освіжає майже все. Прапорець існує саме для цього випадку, тож дешевше вимагати його завжди, ніж вести список винятків.

Часто git тут узагалі не потрібен: які файли змінені — видно через `find -newer`, вміст — читанням файлу.

**Чому межа саме тут.** Пісочниця не має права `unlink` у `.git`, тож будь-який залишений лок вона прибрати не може — його знімає людина на Mac, а наступна сесія отримує «Unable to create '.git/index.lock': File exists». Обхід через тимчасовий `GIT_INDEX_FILE` пробували: 28.07 він дав тихий відкат коміту `dcd6a6c`, який стер три ескалації, ратифікацію CEO і цілий цикл у `state.md`. Врятував лише провалений push. Подробиці — `decisions-log.md` за 28.07 і 06.08.

**Як знімати залишений лок — на Mac і лише свідомо.** Перед `rm` звірити три речі: розмір (застряглий лок майже завжди 0 Б), `mtime` (свіжий = ознака живої роботи) і `pgrep -fl git`. **Ніколи не видаляти лок, яким володіє живий процес** — це псує індекс паралельній сесії. 04.08 цією перевіркою знято чотири локи одразу (0 Б · застарілий mtime · `pgrep` порожній); вона і є різниця між прибиранням сміття й диверсією в чужу роботу.

**Перед комітом** звіряти `git rev-parse HEAD` і `git rev-parse origin/main` окремими командами. Розбіжність → спершу `git pull --ff-only`. Звіряти після `git fetch`: порівняння з протухлим `origin/main` нічого не доводить.

**Pre-commit hook** (`.githooks/pre-commit`, разово `git config core.hooksPath .githooks`) перевіряє формат inbox, append-only decisions-log, секції `state.md` і скан секретів. Структурні фейли ловляться детерміновано.

## state.md продукту — фіксована структура
```
# <product-id> · state
## Done
## In progress (+ ким: петля/агент)
## Next (пріоритезовано)
## Tried & failed (що / чому / коли — НЕ повторювати без нових даних)
## Open questions
```
